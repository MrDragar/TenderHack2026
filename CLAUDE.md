# Tender Hack Казань 2026

Кейс «Автозаполнение ключевых характеристик в СТЕ»: по свободному описанию товара
(одежда, мебель, инструменты) найти конечный код КТРУ, заполнить характеристики
в унифицированном виде, поэтапно показать сужение кодов, найти ошибки и объяснить
каждую правку.


## Как отвечать в чате и писать в плане
Коротко, понятным человеку языком, средне-технически, без `вот такого оформления`,
без лишних терминов.


## Правила хакатона (нарушение = дисквалификация или потеря баллов)
- Весь код пишется с 21:00 9 октября до 13:00 11 октября (п. 7.5 положения).
- В готовом решении нет внешних API закрытых LLM и платных поисков. Роутеры LLM
  только к моделям с открытыми весами. Модели открытые, VRAM на инференс до 40 Гб,
  лёгкое лучше тяжёлого, тяжёлое только с обоснованием.
- Данные организаторов не публикуем: data/ никогда не попадает в git (п. 6.17).
- Фич вне ТЗ не делаем, за них нет баллов. ТЗ и критерии: docs/task.md.
- Решение одной системой, которая проходит весь путь от текста до кода.
- Linux, веб-интерфейс в стиле UI-кита Портала поставщиков.


## Стиль кода
- **Лучший код - тот, который не написан**
- **KISS/YAGNI важнее SOLID/DRY.** Простой плоский код: функции, а не классы; прямой
  вызов, а не слои.
- **Комментарии по умолчанию не пишем.** Комментарий только если неочевидно, и тогда
  объясняет «почему», а не «что».
- **Докстринги по умолчанию не пишем.** Только для неочевидного контракта, побочного
  эффекта или ограничения.
- Все изменения прогонять через `ruff check` и `ruff format`
- Не использовать middle dot для разделения контента нигде


## Тесты
- Тесты на happy path и на границы: пусто, опечатки, неполные данные, нет кандидатов,
  несколько кандидатов.


## Никогда
- **pip / poetry** → только `uv`
- **ORM и фреймворки миграций** → обычные SQL-скрипты
- **Комментарии-пересказ кода** → комментарий объясняет «почему» или его нет
