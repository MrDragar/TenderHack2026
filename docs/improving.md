# Как улучшаем этапы

Нынешний pipeline/ это бейзлайн. Каждый этап можно заменить своим решением и честно
сравнить с бейзлайном на одних и тех же входах. Документ для людей и для агентов.


## Что ищем
Не лишний процент, а красивое решение. Красивое значит:
- одна идея, которую можно записать формулой или объяснить за минуту;
- знания берутся из КТРУ, листов портала и статистики по ним, ручных списков нет:
  товары у судей будут другие;
- этап честно отказывается, когда не уверен, и объясняет ответ;
- код варианта в одном файле и читается сверху вниз.

Вариант чуть слабее по числам, но с ясной идеей лучше сильного, собранного из заплаток.
Признаки заплатки: if под конкретное слово, порог под два примера, новый список значений.


## Как устроено
- Вариант это файл variants/<этап>/<идея>.py. Называем по идее, а не по человеку.
- В файле функция с той же сигнатурой, что в contracts/pipeline.py, и тем же именем, что
  в pipeline/<этап>.py:

  | этап | функция | эталон |
  |---|---|---|
  | candidates | find | генератор: загаданная позиция |
  | section | find_section | названия разделов с порчей и товары листа 1 |
  | extract | extract | лист 1: пары товара уже разделены |
  | link | link | генератор: характеристика, значение, вид порчи |
  | narrow | narrow | генератор: код со всеми значениями и без одного |

- Первая строка докстринга модуля это гипотеза одной фразой, её видно в журнале.
- Если варианту нужно чему-то научиться (частоты, словарь, классификатор), он учится сам
  в функции под @cache на справочнике и листах портала, а не на эталоне.
- Судья: `uv run python -m scripts.judge <этап> <идея>`. Вариант base это бейзлайн.
- Победивший вариант переносится в pipeline/ вместо бейзлайна: система остаётся одна.


## Что показывает судья
- У каждого примера один исход: верно, отказ или неверно. Цена 0, 1 и 2: молча неверный
  ответ хуже честного «не знаю».
- Таблица переходов: строка это исход у бейзлайна, столбец у варианта. Под таблицей
  примеры по клеткам, сначала самые дорогие: «отказ → неверно», «верно → неверно».
- Все примеры прогона лежат в data/eval/runs/<время>-<этап>-<идея>/items.json вместе
  с копией варианта. Журнал всех прогонов: data/eval/journal.jsonl.


## Цикл одного эксперимента
1. **Прочитать ошибки.** Прогнать `scripts.judge <этап> base` или последний лучший
   вариант, открыть items.json, прочитать 20–30 ошибок и отказов, каждой записать причину
   своими словами. Виды ошибок не придумывать заранее, только после чтения.
2. **Сгруппировать.** Взять самую большую группу. Группа из 2–3 примеров не стоит идеи.
3. **Дойти до механизма.** Спрашивать «почему», пока ответ не станет общим. Не «нет слова
   тумбочка», а «товар называют уменьшительным словом от названия позиции». Проверка:
   объясняется за минуту, работает без единого слова про мебель, сработает на одежде.
4. **Записать гипотезу и предсказание до прогона:** какая клетка таблицы должна
   измениться и примерно на сколько, и что ничего не станет хуже.
5. **Минимальный вариант.** Скопировать pipeline/<этап>.py в variants/<этап>/<идея>.py
   и поменять одно место, то, что реализует идею.
6. **Прогнать и сверить с предсказанием.** Клетки «→ неверно» прочитать целиком.
7. **Решить.** Сработало: дописать вывод вторым абзацем докстринга, следующую идею делать
   новым файлом поверх этого. Не сработало: записать почему и оставить файл, отрицательный
   результат тоже результат.
8. Несколько идей объединять только в конце и только доказанные по отдельности.


## Dev и test
- Пятая часть позиций КТРУ, разделов и товаров листа 1 отложена в test (held_out
  в scripts/generate.py). Делим по позициям, а не по текстам.
- Отложенные фразы как у судей кладём в data/eval/test/gold.json в формате gold.json:
  новые фразы сначала туда, их никто не читает.
- Test запускает только человек: `uv run python -m scripts.judge <этап> <идея> --test`
  и `uv run python -m scripts.measure --test`. Судья показывает число, только если цена
  заметно ниже прошлой лучшей, иначе повторные запуски подгоняют решение под test.


## Правила для агента
- Правишь только свой файл variants/<этап>/<идея>.py.
- Судью, генератор, эталон и data/eval не трогаешь. Test не запускаешь и не читаешь.
- Ошибки читаешь в items.json, а не по выводу терминала.
- Никаких ответов под конкретные примеры из dev и ручных списков слов.
- В конце: файл варианта, вывод судьи и одна строка вывода в докстринге.


## Идеи для старта
- **candidates:** TF-IDF по символьным n-граммам по названиям позиций и их текстовым
  значениям: опечатки и формы слов ловятся без словаря; уверенность как вероятность,
  отказ ниже порога.
- **section:** слабая разметка: у товара листа 1 названия характеристик, у раздела
  листа 2 свой набор названий, раздел с лучшим покрытием и есть метка. На таких метках
  обучить классификатор по названию товара.
- **extract:** словарь «как пишут → название характеристики», собранный из пар листа 1.
- **link:** зашумлённый канал: значение КТРУ, к которому текст приводится самой дешёвой
  порчей; цены порч оцениваются по частотам, а не задаются руками.
- **narrow:** уже по энтропии, трогать в последнюю очередь.
