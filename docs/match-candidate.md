# Как работает скрипт

Скрипт решает задачу **блокинга**: для каждой СТЕ из xlsx-файла найти КТРУ из JSON, чьё название похоже на название СТЕ, и вернуть список пар-кандидатов. Никакой финальной верификации по характеристикам здесь нет — это отбор кандидатов, который потом можно докрутить.

Ниже — по шагам, что происходит при запуске.

---

## 1. CLI и точка входа (`main`)

`argparse` принимает четыре аргумента:

- `--ste` — путь к xlsx с СТЕ (читается первый лист);
- `--ktru` — путь к JSON с КТРУ;
- `--out` — куда сохранить результат (`.xlsx` — два листа, `.csv` — только сводка);
- `--min-score` (по умолчанию 60) и `--top-k` (по умолчанию 10) — параметры блокинга.

Дальше четыре шага: `load_ste → load_ktru → blocking → summarize`, затем запись файла и печать короткой статистики в stdout.

---

## 2. Нормализация текста (`norm`, `tokens`)

Обе стороны (СТЕ и КТРУ) приводятся к единому виду:

- нижний регистр, `ё → е`;
- удаление пунктуации (всё, кроме букв/цифр/пробелов);
- схлопывание пробелов;
- `tokens()` дополнительно убирает короткие токены (≤ 2 символов) и небольшой список стоп-слов (`для`, `тип`, `вид`, …).

Эти функции — фундамент, потому что и инвертированный индекс, и метрика схожести работают по нормализованным строкам, а не по «сырым» названиям.

---

## 3. Этап A: парсинг СТЕ (`load_ste`, `parse_ste_chars`)

`load_ste` читает xlsx через `pandas.read_excel` (все колонки как строки, `NaN → ''`) и строит список словарей. Для каждой строки сохраняется:

- `id`, `name` (из колонки «Наименование СТЕ»);
- `norm` и `tokens` — уже нормализованное название, чтобы не считать это повторно;
- `chars_raw` и `chars` — характеристики;
- производитель и страна.

`parse_ste_chars` разбивает поле «Характеристики» по `|` и каждый кусок пытается распарсить регуляркой `TAIL_RE` — она ловит «число + единица» в конце строки:

```
"Максимальные обороты на 1ой скорости 350 об/мин"
    → name="максимальные обороты на 1ой скорости", value=350.0, unit="об/мин"
```

Если хвост не найден (например, значение перечислимое: `"Тип патрона Быстрозажимной"`), кусок кладётся как есть с `value=None`. Запятая в числе нормализуется в точку. Возвращается словарь `{имя_параметра: {value, unit}}`.

Этап A нужен, чтобы характеристики СТЕ уже были распарсены — на будущее, когда вы добавите скоринг по ним.

---

## 4. Этап B: парсинг КТРУ (`load_ktru`, `parse_ktru_chars`)

`load_ktru` умеет читать три формата JSON: одиночный объект с ключом `data`, список объектов, либо `{items: [...]}` — в вашем примере это первый случай, поэтому заворачиваем его в список. Для каждого КТРУ берётся `data` (или сам объект), и из него извлекаются:

- `code` — код КТРУ;
- `name` — название, плюс `norm` и `tokens`;
- `chars` — характеристики;
- `okpd2` — код ОКПД2.

`parse_ktru_chars` идёт по массиву `characteristics.characteristic` и для каждого элемента собирает:

```python
{
  'required': <флаг isRequired>,
  'values': [('range', min, max), ('enum', valueCode), ...]
}
```

Ключом словаря служит нормализованное имя характеристики. Так диапазоны вроде `min=0.1, max=1.5` и перечислимые значения превращаются в однородную структуру, пригодную для матчинга.

---

## 5. Этап C: блокинг (`build_index`, `blocking`, `name_score`)

Это ядро. Идея — не сравнивать каждую СТЕ с каждым КТРУ, а сначала сократить число кандидатов по общим токенам.

### 5.1. Инвертированный индекс (`build_index`)

Один раз проходим по всем КТРУ и строим `{токен: [индексы КТРУ, где он встречается]}`. Это дешёвая структура: память O(суммарное число токенов), построение за один проход.

### 5.2. Отбор кандидатов для каждой СТЕ (`blocking`)

Для СТЕ берём её множество токенов и «голосуем»: каждый токен, найденный в индексе, добавляет +1 соответствующему КТРУ. После этого:

- сортируем КТРУ по числу общих токенов (голосов) убыв.;
- берём `top_k` лучших — те, что разделили со СТЕ больше всего слов;
- на этой короткой подвыборке считаем `name_score`.

Так вместо `N × M` сравнений (например, 10 000 × 5 000 = 50 млн) получается `N × top_k` (10 000 × 10 = 100 тыс.) — в сотни раз меньше.

### 5.3. Метрика названия (`name_score`)

Для пары нормализованных названий считается:

```
score = 100 * (0.5 * Jaccard(tokens) + 0.5 * SequenceMatcher(norm_a, norm_b).ratio())
```

- **Jaccard** — доля общих токенов: ловит смысловое пересечение (`дрель-шуруповерт аккумуляторная` ≈ `шуруповерт аккумуляторный`).
- **SequenceMatcher** — символьное сходство: ловит близкие бренды/модели (`bosch psr 14.4` ≈ `bosch psr 14.4 (0603955420)`).

Смесь двух метрик даёт стабильность: если один из сигналов шумит, второй вытягивает.

Пара попадает в результат только если `score >= min_score` (по умолчанию 60). Каждая пара — словарь с кодом и именем КТРУ, id и именем СТЕ, скором и числом общих токенов.

### 5.4. Важные оговорки

- Одна СТЕ может дать **несколько** кандидатов-КТРУ — это by design. Ограничение «1:1» из предыдущего обсуждения здесь сознательно не реализовано: оно требует либо венгерского алгоритма, либо жадного отбора, и без скоринга по характеристикам назначение будет произвольным.
- Один КТРУ может получить **несколько** СТЕ — это нормально и часто отражает реальность (несколько схожих товаров на одну позицию КТРУ).

---

## 6. Сводка (`summarize`)

Плоский список пар превращается в таблицу, где одна строка = один КТРУ:

| ktru_code | ktru_name | ste_count | ste_ids | best_score |
|---|---|---|---|---|

- `ste_count` — сколько уникальных СТЕ заматчилось на этот КТРУ;
- `ste_ids` — список id через запятую;
- `best_score` — лучший скор по этому КТРУ.

Промежуточно пары сортируются по `score` убыв., чтобы `best_score` считался корректно и чтобы в xlsx-выгрузке строки шли от самых уверенных к самым сомнительным.

---

## 7. Вывод

- `.csv` → сохраняется только сводка `by_ktru`.
- `.xlsx` → два листа: `by_ktru` (сводка) и `pairs` (все пары как есть, для разбора).
- В stdout печатается строка статистики: сколько СТЕ, сколько КТРУ, сколько пар, сколько КТРУ получили хотя бы одну СТЕ.

---

## 8. Что сознательно не сделано

- **Скоринг по характеристикам** — парсинг A и B готов, но в `name_score` характеристики не участвуют. Добавляется как ещё одно слагаемое, если нужно различать, например, «дрель-шуруповёрт на 10.8 В» и «на 14.4 В».
- **Назначение 1:1** — требует отдельного шага (венгерский или жадный по скору).
- **Эмбеддинги** — заменены на комбинацию Jaccard + SequenceMatcher: чуть хуже по синонимам, но в разы дешевле по CPU/RAM и без внешних зависимостей.

## 9. Как крутить

- Названия шумные → снижайте `--min-score` до 50, смотрите `pairs`, чистите вручную.
- Много кандидатов на одну СТЕ → снижайте `--top-k` до 5, но тогда рискуете потерять правильный КТРУ, если он не разделил ни одного токена.
- Домен узкий (только дрели, только оксигенаторы) → `min-score` можно смело поднимать до 70–75.
